## Запуск

### 1. Клонування репозиторію

```bash
git clone <repository-url>
cd lead-distribution
```

### 2. Створення .env
Для локального запуску .env можна створити на основі .env.example. Підключення до PostgreSQL налаштоване через Docker Compose.

### 3. Запуск Docker
```bash
docker compose up -d --build
```

### 4. Генерація ключа застосунку
```bash
docker compose exec app php artisan key:generate
```

### 5. Запуск міграцій
```bash
docker compose exec app php artisan migrate
```

### 6. Заповнення тестовими даними
```bash
docker compose exec app php artisan db:seed
```

### 7. Запуск тестів
```bash
docker compose exec app php artisan test
```

Після запуску застосунок доступний за адресою:

http://localhost:8000

## Архітектура

LeadDistributionController відповідає за HTTP-запит та викликає `LeadDistributionService`.

`LeadDistributionService` містить основну логіку розподілу заявок та використовує `DistributionStrategy` інтерфейс для вибору алгоритму розподілу. 
Поточна реалізація використовує `LeastLoadedStrategy`.

Після розподілу генерується Laravel Event, який обробляється Laravel Listener та передає подальшу обробку в Queue Job.

Для зберігання історії змін статусів використовується окрема таблиця `lead_status_histories`.

## Алгоритм розподілу

Для розподілу використовується алгоритм `LeastLoaded`.

Спочатку отримуються всі активні менеджери та кількість їх відкритих заявок зі статусами `NEW` та `IN_PROGRESS`.

Після цього всі нові заявки розподіляються між менеджерами з урахуванням їх поточного навантаження, щоб отримати максимально рівномірний результат.

Неактивні менеджери не беруть участі у розподілі.

Повторний виклик endpoint не розподіляє заявки повторно, оскільки обробляються тільки заявки зі статусом `NEW`.

## Прийняті технічні рішення

- Бізнес-логіка винесена з Controller у `LeadDistributionService`.
- Для можливості додавання інших алгоритмів використовується `DistributionStrategy` інтерфейс та `LeastLoadedStrategy`.
- Вибір стратегії розподілу винесений у конфігурацію Laravel.
- Статуси заявок представлені через PHP Enum `LeadStatus`.
- Зміна заявки та створення історії статусу виконуються в межах database transaction.
- Для захисту від одночасного розподілу одних і тих самих заявок використовується `lockForUpdate()`.
- Для обробки додаткової логіки використовуються Laravel Event та Listener.
- Для асинхронної обробки використовується Laravel Queue Job.
- Для статистики менеджерів використовується окремий SQL-запит без ORM.
- Для основних запитів додані необхідні індекси.
- Основні сценарії покриті Feature Tests.

## Компроміси

Redis дозволений умовами тестового, але не є обов'язковим, тому для поточного рішення не потрібна додаткова інфраструктура.

Для розрахунку часу перебування заявки в роботі не додавалося окреме поле в `leads`. Необхідна інформація береться з `lead_status_histories`.

Поточний алгоритм отримує всі `NEW` заявки одного запуску в пам'ять. Для дуже великої кількості заявок доцільно було б використовувати batch processing.

Для високого навантаження в подальшому можна розглянути Redis для Queue, масштабування Queue workers та додаткову оптимізацію SQL-запитів.
